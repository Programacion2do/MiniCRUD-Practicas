Objetivo del proyecto

Esta guía toma como referencia el ejemplo Mini-CRUD (gestión de Persona) documentado en la wiki del curso y lo usa como modelo para construir un proyecto propio con las dos capas exigidas: Vista completa y Modelo completo.

Qué se entrega al finalizar

  • Un proyecto Maven organizado en paquetes modelo.vo, modelo.dao y controlador.
  • Una capa Modelo completa: clase VO (objeto de datos) + clase DAO (acceso a datos, con almacenamiento temporal en memoria).
  • Una capa Vista completa: página de entrada, formulario de alta, listado, formulario de edición — todas en JSP con EL/JSTL.
  • Un Controlador (Servlet) que conecta ambas capas y resuelve las acciones: agregar, listar, editar, eliminar.
  • Validación de unicidad del código antes de guardar un nuevo registro.

¿Qué es MVC?

El patrón Modelo-Vista-Controlador divide la aplicación en tres responsabilidades separadas. Antes de escribir código, conviene tener clara esta división.

Modelo

Procesamiento de datos y lógica de acceso a la información. Incluye las clases VO (datos) y DAO (operaciones sobre esos datos).

Vista

Interfaz que el usuario ve en pantalla. Páginas JSP encargadas únicamente de mostrar información, sin lógica de negocio.

Controlador

Lógica que coordina entre Vista y Modelo. Recibe la solicitud, decide qué hacer y determina qué vista se muestra a continuación.

Carpeta ≠ Paquete

Una carpeta es una estructura física del disco; un paquete es una organización lógica de Java, declarada dentro de cada archivo con package modelo.dao;. En VS Code, el paquete se crea con la carpeta correspondiente dentro de src/main/java/ y se declara al inicio del archivo — ambos pasos son necesarios.

Capa Modelo — VO y DAO

La capa Modelo se construye en dos clases con responsabilidades distintas: el VO representa un registro; el DAO administra el conjunto de registros.

VO Clase de datos (ej. PersonaVO)

Contenedor simple con los atributos del registro (por ejemplo codigo y nombre), sus constructores, getters, setters y toString(). Esta clase mantiene una interfaz estable aunque el resto del proyecto cambie.

package modelo.vo;

public class PersonaVO {
    private int codigo;
    private String nombre;

    // constructores, getters, setters, toString()
}

DAO Acceso a datos (ej. PersonaDAO)

Centraliza las operaciones sobre los datos. En esta fase, el almacenamiento es temporal (una lista en memoria); más adelante puede migrarse a JDBC sin modificar Vista ni Controlador, porque el contrato público de estos métodos no cambia.

  • agregar(PersonaVO p) — agrega un registro nuevo.
  • getLista() — devuelve todos los registros.
  • obtenerXCodigo(int codigo) — busca un registro por su identificador; se usa también para validar unicidad.
  • actualizar(PersonaVO p) — modifica un registro existente.
  • eliminar(int codigo) — quita un registro por código.

Por qué separar VO de DAO

Esta separación aísla la validación y la persistencia de los datos. El día que el almacenamiento pase de una lista en memoria a una base de datos real, sólo se modifica el DAO — Vista y Controlador quedan intactos porque siguen llamando a los mismos métodos.

4

Capa Vista — páginas JSP

Tres páginas cubren el recorrido completo del usuario: entrada, alta de un registro y listado. Ninguna de las tres contiene lógica de negocio: solo presentan datos que llegan del Controlador.

index.jsp Punto de entrada

Página de bienvenida con dos enlaces de navegación ("Agregar Persona" y "Listar Personas"), cada uno apuntando al Servlet con un parámetro action distinto (?action=agregar, ?action=listar). Usa ${pageContext.request.contextPath} para que los enlaces funcionen sin importar dónde quede desplegada la aplicación.

wiki · Vista index

persona-form.jsp Formulario de alta

Formulario con los campos del registro (código, nombre), enviado por POST hacia el Servlet con action=agregar oculto. Sigue el patrón PRG: el envío se procesa en el servidor y termina en una redirección GET, evitando que un refresh del navegador reenvíe el formulario. El atributo required aporta validación del lado del navegador, pero el servidor igual debe validar y convertir los parámetros recibidos.

wiki · Vista Agregar Persona

persona-lista.jsp Listado

Tabla con los registros existentes, recorrida con <c:forEach> y con <c:if> para el caso de lista vacía ("No hay personas registradas"). Cada columna se completa con Expression Language (${p.codigo}, ${p.nombre}), que invoca automáticamente los getters del VO.

5

Controlador — Servlet

El Servlet conecta Vista y Modelo. Un único punto de entrada (@WebServlet("/persona")) resuelve todas las acciones según el parámetro action.

doGet() — mostrar vistas

  • action=agregar → reenvía a /vista/persona-form.jsp con el formulario vacío.
  • action=listar (o sin acción) → recupera la lista desde el DAO y reenvía a /vista/persona-lista.jsp.

doPost() — procesar datos

action=agregar toma los parámetros del formulario, arma un PersonaVO, lo persiste a través del DAO y aplica el patrón PRG: redirige (no reenvía) hacia el listado.

Esqueleto de referencia

@WebServlet("/persona")
public class PersonaControladorServlet extends HttpServlet {
    private final PersonaDAO dao = new PersonaDAO();

    protected void doGet(...) {
        String action = request.getParameter("action");
        switch (action) {
            case "agregar": /* forward a persona-form.jsp */
            default:        /* listar() */
        }
    }

    protected void doPost(...) {
        // UTF-8, leer action, delegar al método correspondiente
    }

    private void listar(...) { /* dao.getLista() + forward */ }
    private void agregar(...) { /* parsear, dao.agregar(), sendRedirect */ }
}

Por qué PRG (Post-Redirect-Get)

Una operación POST que termina en sendRedirect evita que, al refrescar la página, el navegador reenvíe el mismo formulario y duplique el registro.

6

CRUD completo — editar y eliminar

Con alta y listado funcionando, se agregan las dos operaciones restantes. Se modifican tres piezas: el listado (habilita los botones), una vista nueva de edición y el Servlet (nuevas acciones).

persona-lista.jsp — botones activos

El botón Editar pasa a ser un enlace GET (action=cargarEditar&codigo=${p.codigo}). El botón Eliminar es un formulario POST embebido con confirmación por JavaScript ("¿Eliminar el registro [nombre]?"). GET se reserva para lectura de datos; POST, para modificar el estado.

wiki · Vista Listar Personas (Fase 2)

persona-editar.jsp — vista nueva

Variante del formulario de alta con cuatro diferencias: el campo oculto vale action="editar", el código llega precargado en modo readonly (no se permite modificar la clave), el nombre llega precargado desde ${requestScope.persona.nombre}, y el botón dice "Actualizar" en lugar de "Agregar".

wiki · Vista Editar Persona

Servlet — nuevas acciones

  • GET action=cargarEditar&codigo=... → cargarEditar() busca el registro por código, lo coloca como atributo de request y reenvía a la vista de edición.
  • POST action=editar → editar() actualiza el registro a través del DAO y redirige al listado (PRG).
  • POST action=eliminar → eliminar() quita el registro por código y redirige al listado (PRG).
wiki · Controlador PersonaControladorServlet (v2)

Flujo completo

Listado→Agregar→Formulario→Guardar→Listado
Listado→Editar→Formulario precargado→Actualizar→Listado
Listado→Eliminar→Confirmación→Listado

Validación de unicidad de código

Antes de conectar una base de datos real, conviene validar en el Controlador que el código ingresado no esté repetido — así se evita mostrar al usuario un error técnico de base de datos.

Cambios en el Controlador

  1. Leer y validar el parámetro codigo recibido del formulario.
  2. Consultar dao.obtenerXCodigo(codigo) para verificar si ya existe un registro con ese código.
  3. Si existe (personaExistente != null): guardar el mensaje de error con request.setAttribute("error", ...) y los datos ingresados con request.setAttribute("persona", ...), y reenviar (forward, no redirect) de nuevo al formulario.
  4. Si no existe: continuar con el alta y aplicar el patrón PRG normalmente.

Cambios en la Vista (persona-form.jsp)

Se agrega un bloque <c:if> que muestra el mensaje de error cuando corresponde, y los campos del formulario se precargan con Expression Language a partir de los datos que el usuario ya había ingresado — así no se pierde lo escrito al mostrar el error.

Por qué forward y no redirect en este caso

El forward conserva los atributos de request (error y datos ingresados) sin necesidad de una nueva solicitud del navegador. El redirect, en cambio, perdería esos atributos porque genera una solicitud GET completamente nueva — por eso la validación fallida usa forward, mientras que el guardado exitoso sigue usando el patrón PRG con redirect.

Checklist final

Antes de dar por completo el proyecto, conviene repasar esta lista contra el proyecto propio.

Modelo

  • Clase VO con atributos, constructores, getters/setters y toString().
  • Clase DAO con agregar, getLista, obtenerXCodigo, actualizar y eliminar.
  • Almacenamiento en una estructura en memoria (por ejemplo ArrayList).

Vista

  • index.jsp con navegación hacia agregar y listar.
  • Formulario de alta con validación básica y patrón PRG.
  • Listado con JSTL/EL, sin scriptlets Java.
  • Formulario de edición con código en modo readonly.
  • Botones de editar y eliminar operativos en el listado.

Controlador

  • Un único Servlet que enruta por parámetro action.
  • GET para lectura (mostrar formularios, listar, cargar edición).
  • POST para escritura (agregar, editar, eliminar), siempre con PRG.

Validación

  • Código duplicado detectado antes de guardar, sin exponer errores técnicos al usuario.
  • Datos ingresados conservados en el formulario cuando se muestra un error.
